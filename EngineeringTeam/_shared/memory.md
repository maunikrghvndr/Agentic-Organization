# Repo Memory — detail procedures

Relocated verbatim from `AGENTS.md` → Repo Memory on 2026-10-18 (lossless progressive disclosure). `AGENTS.md` keeps the layout, the constitution and Spec Kit rules, the roadmap, the task-file rules and the one-line pointer to this file. Read this file when `PROJECT_MEMORY.md` nears ~100 lines or needs splitting into `wiki/`, when a recorded fact must be corrected or superseded, when a paper/spec/RFC is used for the first time (`sources/` → `wiki/ref-*`), when a feature spec is created or evolves, and at task completion (memory lint, archive). Templates live in the library's `MemoryTemplates/` folder.

## Rules (verbatim)

- **Grow by reorganizing, never by deleting.** While small, `PROJECT_MEMORY.md` is a single flat file. When it outgrows ~100 lines, split content into `wiki/` topic pages (`architecture.md`, `backend-patterns.md`, `frontend-patterns.md`, `testing.md`, `gotchas.md`, ...) and turn `PROJECT_MEMORY.md` into an index: commands at the top, then one line per page. Sessions read the index first and open only the pages relevant to the task.
- **Update, don't delete.** Remove a fact only because it is wrong or no longer true — and record that as an update with a short note (`updated 2026-07-20: was X, now Y — reason`). If two sources genuinely conflict and it cannot be resolved yet, flag the contradiction explicitly instead of silently picking one.
- **Reference sources.** Papers, specs, and RFCs the implementation follows go in `sources/` (or a pointer file with URL/DOI when the original cannot be committed). Sources are read-only. On first use, ingest once (the `researcher` role owns this, but any role may do it when researcher is not in play): write a `wiki/ref-<name>.md` page distilling only what the implementation needs, with section/equation/page citations, the source version/date, a map from concepts to implementing files (`path:line`), and every intentional deviation ("source says X, we do Y because Z"). Before relying on a source, confirm it is still current — a newer paper/version/approach may supersede it (`researcher`'s job). Sessions read the reference page, not the source; open the source only when the page cannot answer, then update the page.
- **Feature specs are durable.** `analyst` produces `wiki/spec-<feature>.md` for every feature-sized task — the EARS acceptance criteria plus in/out scope. Update it with dated notes as the feature evolves; never delete criteria (only supersede them with a note). Task files in `TASKS/` are process; spec pages in `wiki/` are the contract that survives the task and gets archived-out with it. Reviewers, QA, and any later change to the feature read the spec page first.
- **Lint on completion.** When a task that touched memory heavily completes, sweep for duplicate facts to merge, superseded claims to update, contradictions to flag, and index lines that no longer match their pages. Reconcile — never trim for length.
- Templates live in the role library's `MemoryTemplates\` folder.

## Relocated 2026-10-18 (second pass, verbatim)

- **Project roadmap — the progress board.** `.ai-memory/ROADMAP.md` is the one-glance view of where the project stands: one line per feature or non-trivial task, grouped **Backlog / In Progress / Blocked / Done**, each linking to its task file and spec. It is how you (or a fresh session) re-orient after a context switch and track progress — read it at the start of a task to see the big picture. `planner` adds items when it sequences work; the role working an item keeps its status current (→ In Progress, → Blocked with the blocker); completion moves the item to **Done** with a date and archives the task file. One line per item — detail lives in the task file, never restated here. Trivial changes are not tracked. In a Spec Kit repo, this is the cross-feature view above each feature's `tasks.md`.
- **Spec Kit interop — use it, do not duplicate it.** If the repo uses Spec Kit (`.specify/` present), its artifacts are the source of truth and you read/update *those*, never a parallel copy: the constitution at `.specify/memory/constitution.md`, and per-feature `specs/<feature>/spec.md` (the spec + EARS criteria — `analyst`), `plan.md` (design — `architect`), `tasks.md` (breakdown — `planner`). Do **not** create `.ai-memory/wiki/spec-*` alongside them — that is a second source of truth. If the environment exposes Spec Kit's commands (whichever spelling the installed version uses — `/speckit.<name>` or `/speckit-<name>`), they produce these same artifacts. When the repo has no Spec Kit, use the library's own convention below (`wiki/spec-<feature>.md`).
- **Repo memory is about the repository, not the machine.** Never write environment or tooling state into `.ai-memory/`: missing binaries, failed or declined installs, PATH problems, admin-rights issues, network/sandbox limits, or one-off local setup trouble. Report those in the session and move on. Only record a tooling fact when it is a durable property of the project itself (for example a required runtime version or a build step the repo genuinely depends on). The host's per-machine memory (Claude Code auto memory, Codex memories) is the third store, for machine-local facts and personal corrections — a convenience layer, never a source of truth, never a duplicate of `AGENTS.md`, `PROJECT_MEMORY.md` or `LESSONS.md`; when it captures a durable repo property, promote it to `PROJECT_MEMORY.md` with a dated note. Hosts without such a store (Cursor) report in-session, as today.

## Added 2026-10-19 — conventions inherited from peers (Hermes, cc-sdd, BMAD, Letta, OpenSpec, Spec Kit)

- **Status ownership.** Delivery moves a ROADMAP item to **In Review**; only the user's recorded acceptance (task file Decisions, in their words, dated) moves it to **Done**. Done is never written by the role that delivered or the reviewer that passed it; a consult-only turn writes no status; confirm the group matches reality before the phase ends.
- **Archive naming and gate.** A task file moves to `TASKS/_archive/YYYY-MM-DD-<task>.md` — never overwrite, never stack a second date — and only when every `AC-n` in its spec carries a status (Met + Evidence, or superseded) and the ROADMAP line is Done. Archive when merged/shipped, not when the diff is written. Several finished tasks on one spec page archive in completion order, with one spec-vs-code check per page.
- **Facts, not instructions.** Memory lines are declarative with a reason and a date; never imperatives to yourself (an imperative stored here is re-read as a directive and can outrank the user's request). Anything stale within a week belongs in the task file, not here.
- **Patterns, not catalogs.** Record a pattern once with one `path:line`; code that follows a recorded pattern needs no update.
- **Never in memory:** secrets, connection strings, internal hosts/IPs, agent tooling directories (`.claude/ .codex/ .cursor/ .kiro/`).
- **Admission and supersession.** Admit only what the code cannot say. A pitfall enters after someone saw it (once = dated note; recurrence = Hard Rule). Prefer a prohibition that names the permitted alternative. Style a linter can enforce belongs in the linter — `enforced by <check> since <date>` supersedes the line. A line is superseded (dated, never silently removed) only on four grounds: wrong/stale; mechanically enforced; harmful/contradictory; user-approved. "Nothing failed lately" is never a ground.
- **Verified header.** `PROJECT_MEMORY.md` starts with `Verified: YYYY-MM-DD against <short sha>`; a session that finds it far behind HEAD re-verifies the Commands block.
- **Index-line contract.** Each `wiki/` page has exactly one index line in `PROJECT_MEMORY.md` = what it holds and when to open it; an unindexed page is unreachable; one level; no file/directory stem collisions.
- **Re-sync.** A stale recorded fact found while reading code is fixed in the same phase with a dated note (Code→Memory); Memory→Code drift is a reviewer finding.
- **Procedure pages.** A repeatable 5+-step workflow with exact commands (data/ontology reload, index rebuild, release) is its own `wiki/howto-<name>.md`, indexed from `PROJECT_MEMORY.md`, written the second time it runs.
- **Persistence model.** Living spec is the library default: no role reconciles spec/design/plan automatically — QA appends convergence rows, analyst amends criteria, planner re-syncs. The constitution records `living spec` or `flow-forward` per area.
- **Completion sweep (updated 2026-10-19: the "Lint on completion" line above stays; this is its checklist).** (1) index ↔ page both ways; (2) index descriptions still match their pages; (3) duplicates and contradictions fixed at the source; (4) superseded facts carry a dated note; (5) size is a signal only. Run `Scripts/Lint-RepoMemory.ps1 -RepoRoot <repo>` when available and paste its summary as an Evidence row, or `Not run: <why>` — a sweep without that row did not happen; a proposed fix is not an applied or verified fix; a clean sweep is a valid result.
