## Evidence that applies to every proposal

- The source is vendor reference documentation. It states how the host behaves; it contains no measurement that any of these mechanisms improves an outcome. ### P1. Fail-open contract in `Hooks/README.md` — Adopt now, cut to three bullets. Verification: Confirmed

Evidence: every fact in the five bullets is on the page. Exit 1 is non-blocking (`hooks.md:899` "Exit code 1 without valid JSON output is a non-blocking error … use `exit 2`"); failures let the action through (`:939`); `onFailure` needs v2.1.295 and is `command`/`http` only (`:458`, `:510`, changelog `2.1.295`); it has no effect on `Stop`, `SubagentStop`, `TaskCompleted`, `TeammateIdle` (`:990-992`); matcher exact-versus-regex rule (`:282-285`); matcher on an unsupported event "silently ignored" (`:339`), `Stop` has no matcher support (`:313`); `if` on a non-tool event "never runs" (`:424`); `@`-mentions fire no `PreToolUse` (`:1791`); Bash can still write a protected file (`hooks-guide.md:309`); debug line (`:4355`); `/status` list (changelog `2.1.327`). "Missing" is true: `rg onFailure` over the library returns nothing, and `Hooks/README.md` nowhere says a failed hook lets the action through. Constraints: none broken; an optional overlay's own README, zero session tokens. Value, under the skeptic lens: bullets one to three correct a present misreading. The README says the pack "enforce[s] two of its rules" and that `handoff-check.mjs` "Blocks the stop", while the page says a `Stop` hook cannot be made fail-closed and that a missing script on `Stop` is downgraded to a non-blocking error (`:820`). That case is reachable in this library today: the hook is registered with an absolute `<library-root>` path, and `AGENTS.md` has a whole procedure for a moved library, after which the hook silently does nothing. Bullets four and five (matcher traps, debug) do not survive: they restate the vendor page for hooks this pack does not ship, and they carry three version pins that will drift (the page already moved from v2.1.296 to v2.1.319 between the library's two reads). A one-line pointer to the page sections does the same job. The sentence "every guard hook added to this pack … sets it" is a rule for code that does not exist; keep the fact, drop the rule. One fact the gap file missed and that belongs in the kept text because the library owner runs native Windows: on Windows without Git Bash a failing shell-form `PreToolUse`/`PermissionRequest` hook blocks, and stops blocking once Git for Windows is installed (`hooks.md:943`), so the same config fails closed or open by machine.

### P2. Hook escalation paths in `security-engineer.md` — Adopt after an eval, narrowed. Verification: Probable

Evidence: the six facts are on the page (`PermissionRequest` `updatedPermissions`/`setMode`, `CLAUDE_ENV_FILE` at `hooks.md:1391`, skill hooks "for the rest of the session" at `:683`, HTTP hooks, fail-open as above). The changelog fixes the gap file cites (2.1.77, 2.1.110, 2.1.222, 2.1.292) are host bugs that were fixed; they show the surface is risky, not that a reviewer line catches anything. "Missing" is only partly true: `security-engineer.md:706` already lists "permission widening (`bypassPermissions`, allow-lists, `dangerously-*` flags), and persistence via a hook or settings edit that a later session will execute", `:710` already says "prose is never the only control", and `_shared/rules-detail.md:22` already classes every hook file as executable code that gets this review. What is new is narrow: (1) "a hook presented as a control must fail closed, or be recorded as a nudge" and (2) "a hook that answers permission prompts or writes permission rules is a permission widening". Those two are host-neutral and worth a line. Items (3) to (6) are Claude Code detail (rewriting tool I/O, the env file, HTTP hook URLs, skill-frontmatter hooks); in a role file every host reads they are lock-in by example, and they add about 700 bytes that load in every security phase on every host. Constraints: full-depth holds (addition only). One real defect in the wording: the proposed addition to the `Block any of:` sentence makes "a hook that … rewrites tool input or output" Blocking with no qualifier, which would block a legitimate, approved hook (for example one that adds a redaction flag). The existing sentence qualifies widening with "the user did not approve under ask-first"; the new clause needs the same qualifier. Value: a solo developer adds a hook a few times a year, and the reviewer already reads it as code. Why an eval and not now: this is the one proposal with a per-session cost, and there is no evidence the existing wording misses these cases. Gate: one trap in `Evals/trap-tasks.md` — a diff that adds (a) a `PreToolUse` guard that exits 1 and (b) a `PermissionRequest` hook that returns an allow rule — reviewed by `security-engineer` as it is today. If the current role file flags both, Reject P2 as duplication; if it misses either, adopt items (1) and (2) only, with the qualifier fixed.

### P3. Bound and reword the re-entry hook output — Defer. Verification: Confirmed (host fact); the claimed failure is not shown

Evidence: the "verify first" item is resolved. The cap applies to plain stdout as well as `additionalContext` (`hooks.md:1091` "and its plain stdout, are capped at 10,000 characters"; `:1094` over the limit the output is replaced by "the file path and a preview of up to the first 2,000 characters"; "Claude Code doesn't ask Claude to read the file"). `session-reentry.mjs:94-99` writes with no limit; "Missing" is true. The value claim does not hold up on two counts. First, size: measured over this repository's open task files, the largest `## Summary` + `## Handoff` is 4,871 characters (`library-field-review-2026-10.md`), about half the cap; the gap file's "overflows on a long task" has no instance behind it. Second, consequence: on overflow the model still receives the first 2,000 characters, and the hook prints `REENTRY_LINE` and `Task file: <path>` first, so the two things the hook exists to deliver (re-read the task file, and which file) survive. The gap file's "fails exactly when it is needed, with no visible error" is wrong; what is lost is the inline copy of the tail, which the first line already tells the model to read from disk. The rewording rests on real guidance (`hooks.md:1197` "factual statements rather than imperative system instructions") but there is no report that the current line trips the defense, and the current line is a pointer to a rule in `AGENTS.md`, not an out-of-band system command. Cost: a change to executable hook code plus a test plus the security pass, for a case not yet seen. Cheaper way: none needed now. Trigger to revive: a task file whose Summary + Handoff passes about 8,000 characters (a one-line check in `Scripts/Lint-RepoMemory.ps1` would surface it), or one observed session where the re-entry text was surfaced to the user instead of used as context.

### P4. Load check for `AGENTS.md` — Adopt now, wording corrected. Verification: Confirmed

"Missing" is true: no library file mentions `/context all`, `/memory` as a load check, or `InstructionsLoaded`. Two facts the gap file did not carry and the sentence needs: before v2.1.280 `/memory` and `/context` did not list a directly read `AGENTS.md` (`memory.md:614`), and an interactive session already prints `no CLAUDE.md found; AGENTS.md loaded: <path>` at start (`:378`), which is the cheapest check of all. ### P6. Correct the "one trust dialog" claim — Adopt now, drop the word "cloud". Verification: Confirmed

Evidence: `hooks.md:4291` "**`-p` or SDK session**: Claude Code never shows the dialog and treats the folder as trusted, so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted"; `headless.md:41` "Without `--bare`, a `-p` session runs the hooks in a project's `.claude/settings.json` … even in a folder you've never trusted". The "verify first" item is resolved: `headless.md:37` "`--bare` … skipping auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory, and CLAUDE.md", and `hooks.md:734` confirms `--settings '{"disableAllHooks": true}'` overrides project settings for one run. The library text is wrong as written in three places (`Hooks/README.md:3`, `README/ORCHESTRATION_README.md:180`, `Scripts/Sync-AgentsMd.ps1:29-30`): it places a trust dialog in front of `-p` runs, and there is none. Constraints: none; a correction, not a new rule, zero session tokens. It strengthens the security posture text, so the `security-engineer` pass applies. Value: this is the one proposal that fixes a false safety statement, and it is the case the Rule of Two paragraph is about (a headless run over a repository you did not write). One correction: the proposed replacement says "`-p`/SDK/cloud session with no dialog at all". The page states it for `-p` and SDK only; I found no line that states trust behavior for cloud sessions. Write `-p`/SDK, and leave the cloud sentence as a separate, unverified statement or remove it.

### P7. Widen the `CLAUDE.md` shadow check — Adopt now, with one required exclusion; drop two README clauses. Verification: Confirmed

Evidence: `memory.md:373` "**Count** …: a `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` in your working directory or any directory above it"; `Sync-AgentsMd.ps1:155-168` tests each repo root only. The "verify first" item is resolved, and it matters: `memory.md:374` "**Don't count**, and keep loading alongside `AGENTS.md`: your `~/.claude/CLAUDE.md`, your organization's managed `CLAUDE.md`, and `.claude/rules/` files" (repeated at `:608`). The proposed walk tests `.claude\CLAUDE.md` in every ancestor including the user profile folder, and `<home>\.claude\CLAUDE.md` is exactly the file that does not count. As written the check would warn on every machine that has a user-level `CLAUDE.md`. The exclusion is required, not optional: skip `<home>\.claude\CLAUDE.md`; a `CLAUDE.md` or `CLAUDE.local.md` directly in the home folder does count when the repos live under it. Constraints: script warns and never blocks (unchanged behavior), no dependency, zero session tokens; executable script, so tests and the security pass apply. Value: one stray file in the repos folder turns the library off on this host for every repo while the sync script reports all healthy. No instance observed; the cost is about ten lines. README Target B: keep "A `CLAUDE.md` or `CLAUDE.local.md` in any parent folder shadows it as well" (the current "Any `CLAUDE.md` in the repo shadows it" is incomplete). Drop "Not loaded from `--add-dir` directories": per `memory.md:156` a `CLAUDE.md` is not loaded from those directories by default either, so this is not a difference a user of this library meets (`:431` only applies with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` set). Drop the Bedrock/Vertex clause unless the owner uses those; it is true (`:422`) but adds a version pin for a setup not in evidence.

### P8. Lint the `Rules/` frontmatter — Defer. Verification: Confirmed (host fact)

Evidence: `memory.md:255` "If the YAML between the markers doesn't parse, Claude Code ignores the frontmatter and loads the rule as if it had no `paths`. Run `claude --debug` to see the parse error." No such check exists in `Lint-Library.ps1`; "Missing" is true. Against it: four files of 430 to 851 bytes, copied verbatim by the sync script, all four with valid frontmatter today (checked), and edited rarely. The failure costs under 1 KB of context per session and drops nothing, as the gap file says itself. The proposed check is a regex stricter than the host: the page accepts "a YAML list or a comma-separated string" (`memory.md:253`), so the lint would flag frontmatter the host reads correctly, and it still would not catch every YAML error. Adding a lint rule is a permanent maintenance line in a script the security pass must re-read. Trigger: a fifth rule file, any edit to a `Rules/*.md` frontmatter block, or one observed rule loading unscoped.
