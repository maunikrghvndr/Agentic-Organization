## P1 — Check configuration is a check

- **Verdict:** **Adopt now** for (a) the reviewer mechanical step and (b) a rule limited to weakening an existing check. **Reject as worded** for "adding a suppression is ask-first, recorded as an Approval" applied to every new inline suppression.
- **Verification:** Confirmed for the gap, Probable for the value.
- **Evidence.** Source confirmed: `scripts/hooks/config-protection.js:5-7` "Blocks modifications to linter/formatter config files. Agents frequently modify these to make checks pass instead of fixing the actual code." Unit test exists (`tests/hooks/config-protection.test.js`, not run). No outcome data. Two facts the gap file did not carry over: the hook deliberately does not match `tsconfig.json` (`:113-116` "editing a bundler or test-runner config is ordinary work, and sweeping those in would make the hook obstructive") or `pyproject.toml` (`:56-58`), and it has no inline-suppression check at all. So the proposal is wider than its source on three points, and the source's authors judged two of them too obstructive.
- **Is it missing?** Mostly yes. My search for `eslint-disable|ts-ignore|pragma warning|SuppressMessage|noqa|NoWarn|TreatWarningsAsErrors` across the library returns nothing; the nearest lines are "Do not suppress type errors casually" (`frontend-engineer.md:351`, `frontend-reviewer.md:518`) and "Do not weaken tests to make them pass" (`backend-engineer.md:1318`, `frontend-engineer.md:1058`). One part is already covered and the gap file missed it: `Directory.Build.props/targets` is in the agent-configuration list (`rules-detail.md:25`), so a `NoWarn` change there is already ask-first with a security pass.
- **Constraints.** None broken; prose plus `rg`. Two costs. First, an ask-first item in an unattended run is a denial (`rules-detail.md:87`), so a legitimate `# type: ignore` on an untyped third-party import, or an `@ts-expect-error` in a test of invalid input, would stop a headless run. Second, the same item pasted into `backend-reviewer.md` and `frontend-reviewer.md` adds to the 19 duplicate blocks `Lint-Library.ps1` W2 already reports for that pair (`EVALS.md` results log).
- **Value.** The failure is real and cheap for an agent to commit: reviewer mechanical check 6 (`backend-reviewer.md:87`) runs the recorded lint command, and a relaxed config makes that command pass. Nothing today makes the reviewer look at what the lint run was configured to check. Cost: about 300 bytes in each of two reviewer files that are 36 KB and 31 KB.
- **What to land.** (1) The reviewer item as proposed, with the consequence changed: a relaxed rule, lowered threshold or disabled check in an existing config without a recorded Approval is Blocking; a new inline suppression is listed with its rule id and must carry a one-line reason in the code, Blocking only when it has none or when it silences a failure this diff introduced. (2) One clause on the engineer lines that are already loaded (`backend-engineer.md:1318`, `frontend-engineer.md:1058`): "nor relax a lint, analyzer or type-check rule or threshold to make a check pass". (3) The `rules-detail.md` section as the reference text, with `tsconfig*.json` kept (strictness flags only) and the ask-first limited to existing-config weakening. Drop `@ts-expect-error` from the Blocking set: it is the form that fails when the error disappears.

## P2 — Hook bypass forms

- **Verdict:** prose bullet **Adopt now**, reworded; Settings patterns **Defer**. Trigger to revive: the next scheduled re-verification of `Settings/README.md` against the permissions doc, or the first recorded bypass through a form other than `--no-verify`.
- **Verification:** Confirmed for the source and for the gap as corrected below; Unverified for the pattern syntax.
- **Evidence.** Source confirmed: `scripts/hooks/block-no-verify.js:5` blocks `--no-verify` and `-c core.hooksPath=`; `:180-190` handles `commit -n` including clustered short flags (`-an`); `:14-20` states the limit ("it does not prove that none can run"). Two corrections to the proposal: `HUSKY=0` and `SKIP=` appear nowhere in the source hook (`grep -c` returns 0), so that part is the gap author's addition, not ECC's; and the source needed 1,516 lines and a shell model to match these forms without false positives, which is evidence that a few glob patterns will not.
- **Is it missing?** Narrower than stated. The gap file says "on two of three hosts nothing says a hook may not be skipped". Two existing lines apply on every host: `AGENTS.md:113` "Weaken tests, validation, or security checks to make something pass" (the gitleaks pre-commit is a security check), and `devops-engineer.md:84` "Preserve deployment gates, approvals, required checks, and branch protections. Never bypass or weaken them to make a build pass." What is missing is the word "hook" and the named forms. `Settings/claude-baseline.settings.json:62,83` covers the literal `--no-verify` only, as claimed.
- **Constraints.** The prose bullet breaks none. Target 2 is agent configuration (ask-first, security pass). Its patterns are unverified: `Bash(* core.hooksPath*)` would also prompt on the install command the library itself documents (`Settings/README.md:51`), which is acceptable for an ask rule; whether `Bash(HUSKY=0 *)` matches a command with a leading environment assignment was not checked against the permissions doc. `Settings/README.md` already says text-matched rules are "defense in depth, not a boundary".
- **Value.** Skipping a failing hook is one of the commonest ways an agent gets a commit through. The secret gate is the only hard control that works on all three hosts, and `--no-verify` or `commit -n` removes it. Cost of the prose: one bullet, read on demand.
- **What to land.** The bullet in `rules-detail.md` → Git discipline, minus the claim that it is an ECC list for `HUSKY`/`SKIP` (cite them as the library's own additions), plus one clause where it will be read: the engineer "Do not weaken tests" lines or the reviewer Mechanical Checks ("a commit made with a hook bypass and no recorded Approval is Blocking"). Without that clause the bullet sits in a section nothing points to.

## P3 — Evaluating a gate: placebo arm and grader validation

- **Verdict:** **Adopt now**, shortened and scoped to gates added after this date.
- **Verification:** Confirmed.
- **Evidence.** This is the one proposal with outcome data behind it, and I re-read all of it. `docs/gateguard/question-effectiveness.md:445-475`: "96 trials as planned ... `gate` 25 of 48 (52%), `off` 18 of 48 (38%) ... exact two-sided McNemar p is **0.210** ... **not confirmed**"; "about 37% more turns and 40% more cost"; `:166-180` pilot 18/18 in every arm with "about 45% more turns and 28% more tokens"; `:488` "needs about **177 pairs** for 80% power"; `:34` reference must score 1 and `naive` must not; `:430` "No extension". Every number in the proposed reference line matches. The method also showed it works as a method: the pilot's all-pass result was diagnosed by exactly the two rules proposed (facts discoverable in the repo; assertions true by construction).
- **Is it missing?** Yes. `EVALS.md` has trials per arm, a noise floor, a mechanical check and trap tasks (`:31-37`). It has no placebo arm and no grader check (`rg 'placebo|naive|reference solution'` returns nothing). Its "When to run one" list is about trimming.
- **Constraints.** None. `EVALS.md` is not loaded per session: token cost 0.
- **Value, and the skeptic's objection.** The results log reads "(none yet)": no A/B has been run under the current protocol. A three-arm, pre-registered protocol added to one that has never been run is likely to stay unread. Two more problems with the wording: "a gate does [need an A/B], before it becomes a default" would, read literally, apply to gates the library already has (the Grill Checkpoint, the Stop hook) and none was tested; and three arms at three trials each triples the cost of a protocol whose first run is still pending.
- **Why it survives anyway.** The decision it protects is live: this sweep is producing proposals for new mandatory steps, and the single measured datapoint says such a step costs 35-45% more turns with no confirmed gain. Recording that number and the grader rule costs nothing per session.
- **What to land.** Keep: the definition of a gate, grader validation (applies to every eval, so place it under "What every run records"), the discoverability rule, the mandatory cost column, the reference datapoint. Change: placebo arm is "add when the gate interrupts the agent", not a fixed third arm; add "applies to gates proposed after 2026-11; existing gates are candidates, not violations". Add the pilot numbers to the reference line (45% turns, 28% tokens, 72 sessions) since the cost figure is, in the source's words, "the most reliable number in the evaluation".

## P4 — RED must fail for the intended reason

- **Verdict:** **Adopt now** with one wording fix.
- **Verification:** Confirmed for the gap, Probable for the value.
- **Evidence.** Source confirmed: `skills/tdd-workflow/SKILL.md:177-179` "The compile failure is itself the intended RED signal ... the failure is caused by the intended business-logic bug, undefined behavior, or missing implementation ... not caused only by unrelated syntax errors, broken test setup, missing dependencies, or unrelated regressions". It is skill prose with no hook and no measurement, as the deep read said. The rule itself is the standard test-first check, not an ECC invention.
- **Is it missing?** Yes. `AGENTS.md:106`, `backend-engineer.md:1466`, `frontend-engineer.md:1205` and reviewer item 5 (`backend-reviewer.md:86`, `frontend-reviewer.md:95`) all require a failing-before row and say nothing about why it failed. The Evidence row format allows "output path or first failing line" (`TASK_MEMORY.template.md:34`), so a row can satisfy the rule without showing the failure at all.
- **Constraints.** None. One sentence in four files that are already loaded for the phase; about 200 bytes each.
- **Value.** A RED that fails on an import error proves nothing, and the GREEN that follows proves only that the import was fixed. The reviewer has no way to see this today because the row need not quote the failure. This is the cheapest proposal in the set and it closes a hole in a rule the library already treats as central.
- **Wording fix.** "The RED row's first failing line must be the assertion on the AC's behavior" is too narrow: a legitimate RED is often an exception thrown from the code under change (`NotImplementedException`, a null dereference in the method being fixed), not an assertion. Use: "The RED row quotes the first failing line, and that line is a failure of the behavior under change (an assertion, an exception raised from the code under change, or the compile error the AC implies); a failure in setup, imports, fixtures or syntax is not RED."
- **Not adopted from the source, correctly:** per-stage checkpoint commits. Commit policy belongs to the project constitution (`rules-detail.md:76`).

## P5 — Finding precision

- **Verdict:** the failure-scenario requirement **Adopt after an eval**, scoped to correctness findings in `backend-reviewer` and `frontend-reviewer`. The "Blocking `none` is a valid result" sentence **Reject**: already covered.
- **Verification:** Confirmed for the source text, Probable for the risk.
- **Evidence.** Source confirmed: `agents/code-reviewer.md:39` "Pre-Report Gate", `:55-64` "HIGH / CRITICAL Require Proof ... The specific failure scenario: input, state, and outcome ... Why existing guards ... do not ... If you cannot produce all three, demote to MEDIUM or drop", `:66` "It Is Acceptable And Expected To Return Zero Findings", `:27` ">80% sure". No evidence anywhere in the repo that these rules improve precision or that they do not reduce recall. The gap file says the same.
- **Is it missing?** Half. The "zero findings" part exists: `AGENTS.md:175` requires "Blocking (state `none`)" and a `Checked, nothing found:` roll-up, and all reviewer report templates use it. The failure-scenario part is missing: the `Probable` label needs only a "concrete `path:line` chain" (`backend-reviewer.md:986`).
- **Constraints: this is where it fails as worded.** "A Blocking finding states the failure scenario (input or state → wrong result)" covers every Blocking finding. Many of the library's Blocking findings have no input-to-wrong-result form: a placeholder hit, a missing Evidence row, a dropped `AC-n`, spillover outside `Owns:`, a hardcoded message, a missing `security-engineer` record, a constitution violation. Under the proposed text a reviewer that cannot write a scenario must label these `Unverified`, and `Unverified` cannot block. The trailing "Style rules stay Blocking" clause protects one of those classes only. Applied to `security-engineer`, it would also demote defense-in-depth findings, which weakens a security rule. The source avoids this because its severity scale has no rule-based blocking class; the library's does.
- **Value.** A false Blocking finding costs one of three rework rounds, so the failure is real. But the library already has two guards the source lacks: the `Confirmed/Probable/Unverified` label and a fresh-context re-review. No recorded lesson or trap task shows false Blocking findings happening here (`Evals/trap-tasks.md` has eight rows, none about reviewer false positives).
- **The eval.** One trap pair per `Evals/trap-tasks.md` rules, though the trap would be new and not from a recorded failure, which that file forbids ("never invented toys"). So the honest trigger is: adopt after the first recorded case of a Blocking finding that a guard already handled, then test with that case as the trap (planted defect with no guard, decoy behind a guard; measure both caught-defect rate and false-block rate).
- **If it lands,** the wording must say: applies to findings about runtime behavior only; rule-based findings (mechanical checks, AC trace, style rules, constitution, missing security record) block on the rule, with no scenario; `security-engineer` is excluded. Target 2's "same bullet in the other four reviewer files" also needs correcting: `data-reviewer.md:78`, `ml-reviewer.md:73` and `ai-reviewer.md:97` use a one-line finding format, not an "Each finding must include" list.

- **Is it missing?** Yes as a single view. The facts are in `AGENTS.md:78`, `Hooks/README.md` ("Not shipped") and `Settings/README.md`. The Host compatibility table (`README/ORCHESTRATION_README.md:155-164`) covers discovery of `AGENTS.md` only.
- **Hook claims re-checked against the code.** `handoff-check.mjs` spawns `git` only (`:28,55`). `session-start-library.mjs` runs `git clone --depth 1 --branch <ref> <LIBRARY_URL> <libraryRoot>` (`:91`), so "network" and "writes outside the repo" are right. No hook file contains `fetch(`, an HTTP client or a model CLI call. The proposed sentence "None sends session content to a model or a remote service; none edits source files" is true of the four files at `b8bc665`.
- **Cells that are wrong.**
  - "Re-entry after compaction — Enforced when installed". `session-reentry.mjs` "Never blocks" (`Hooks/README.md:8`); it adds text to context. That is not enforcement. Use a fourth state, for example **Assisted** (a shipped overlay supplies the input; nothing blocks).
  - "Secret gate — Enforced (git, any host)" in all three columns. It is enforced only when the hook is installed, only at commit time, and it is skipped by `--no-verify`, which is prompted on Claude Code with the baseline and nowhere else. Write "Enforced when installed; bypassable by a hook skip (see P2)".
  - "Fresh-context reviewer — Enforced when installed". The shim makes a fresh context available; nothing forces the session to use it. `AGENTS.md:78` words it as "runs as the matching reviewer subagent when installed" with a fallback. This is **Assisted**, not Enforced.
- **Constraints.** README is documentation. `Hooks/**` is in the agent-configuration list (`rules-detail.md:21`): ask-first plus a `security-engineer` record for the column. Token cost per session 0. Maintenance: one more dated table to re-verify when a host changes; the library already carries that duty for the table above it.
- **Value.** A Codex or Cursor user who reads "deny baseline" and "Stop check" in `AGENTS.md:78` can assume they are protected. One table fixes that, provided it does not itself overclaim.
