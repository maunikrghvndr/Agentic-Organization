## 2. Proposals

Ordered by value. Wording is in the library's style and meant to be pasted. Byte cost in `AGENTS.md` is 0 for all of them. Sizes are approximate.

### P-1 — Done-when names its failing direction and is not already true (mechanisms 15, 16)

- **Target:** `EngineeringTeam/planner.md`, Pre-Implementation Gate. Insert one bullet directly after line 78 ("**Every phase has a verifiable done-when** ...").
- **Wording:**
  `- **Every done-when is falsifiable.** It names the exact check (a command recorded in \`PROJECT_MEMORY.md\`, or the full command) and the output that means failure. A done-when that already holds at the \`Baseline:\` sha is not a check: rewrite it, or record the value beside it as \`at Baseline: <value>; expect: <op> <value>\`. A check that cannot run in this repo is a gap, not a done-when (HIGH).`
- **Also:** `planner.md:193` template line, append ` — fails when: <output>`. `MemoryTemplates/TASK_MEMORY.template.md:16` needs no change.
- **Cost:** about 430 bytes in `planner.md`.
- **Lost by not adopting:** a phase can be closed by a check that was green before any work, or by a command nobody could run; the RED row catches this for tests only, and only at review time. The source records a planner emitting 21 unrunnable verification commands that passed "by luck".

### P-2 — Evidence-tagged criteria (mechanism 9)

- **Target 1:** `EngineeringTeam/analyst.md`, after line 135 ("Keep one testable behavior per criterion ...").
  `A criterion whose pass cannot be read off the spec and the code (behaviour under load, against a real external system, on production-shaped data, a judgement of output quality) carries \`[evidence: <the run or observation that proves it>]\`. The tag is set here, at spec time, never by the role that later verifies it.`
- **Target 2:** `EngineeringTeam/qa-engineer.md`, in the Rules list after line 454.
  `- A criterion tagged \`[evidence: ...]\` is Met only with an Evidence row for that exact evidence; a green unit test or a code read scores it \`Not verified (evidence not produced)\`, never Met.`
- **Cost:** about 330 + 220 bytes.
- **Lost by not adopting:** the decision "this cannot be verified from here" stays with the verifier, which is the party the source reports as confidently passing blind-spot checks (their figures: about 100% false pass, 17% with an external tag, 67% when merely told to abstain; raw data not in their repo, so Unverified). The library already has the verdict word; it lacks the spec-time trigger.
- **Eval first:** one trap task in `Evals/trap-tasks.md` (an AC that needs a real external call, with a mock-only test available); pass = the QA row is `Not verified`, not Met.

### P-3 — Prohibition criteria (mechanism 10)

- **Target 1:** `EngineeringTeam/analyst.md`, grill list, after line 77 ("What is explicitly out of scope?").

- **Target 2:** `EngineeringTeam/analyst.md`, EARS list, after line 122.
  `- **Prohibition (must never happen):** \`THE SYSTEM SHALL NOT <behavior>\` — a standing rule, not the handling of one event; QA traces it with a negative test that attempts the behavior.`
- **Target 3:** `EngineeringTeam/qa-engineer.md`, Rules list after line 461.
  `- **Prohibition criteria** (\`SHALL NOT\`): the covering test attempts the forbidden behavior and asserts it did not happen; a test of the permitted path does not cover it.`

- **Cost:** about 130 + 230 + 190 bytes.
- **Lost by not adopting:** must-never rules only surface if the user volunteers them or `security-engineer` infers them after the code exists; "Out Of Scope" records what will not be built, not what must not occur. The source's own test found its edge probe caught 0 of 8 prohibitions (Unverified figure), which is the argument for asking the question separately.
