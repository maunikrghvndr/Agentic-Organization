## 2. How it actually works

The skill is a set of instructions for a "parent" agent that coordinates sub-agents. All enforcement outside the two validators is by prompt.

**Two modes** (`SKILL.md` "Operating modes"): "This skill is guidance by default. Loading it does not authorize the complete audit workflow or file creation." Full audit mode runs only on an explicit audit or pen-test request or a request for report artifacts; "If the request could mean either mode, ask one focused question before creating files".

**Roles** (`SKILL.md` "Platform terminology"): Parent (coordinates, "owns shared state"), `research` agent (source exploration, read-only), `general` agent (investigation and bounded local execution).

**Setup** (`SKILL.md` "Full audit setup"): output directory defaults to `~/security-audit-skill/<repo-name>/run-<N>`, outside the target; a directory inside the target is allowed only if the user selects it and "the parent verifies that version control ignores the whole directory". The parent writes `run-metadata.json` (run id, source ref, profile, scope paths, budget, `execution_policy: "sandboxed-source-and-local-only"`, `run_status: "in_progress"`) before delegating.

**Phase 1 — reconnaissance** (`RECONNAISSANCE.md`): four parallel read-only `research` agents with fixed prompts (1a product/stack, 1b principals and controls, 1c entry surfaces and sinks, 1d local execution and deployment visibility). "They return structured facts to the parent and do not write files." The parent writes `architecture.md` ("hard cap of about 1,000 words") and seeds `coverage-ledger.json`, one unit per "material combination of entry surface, trust boundary, subsystem, and applicable ordinary or companion attack class".

**Phase 2 — hunting waves** (`HUNTING.md`): the parent assigns `planned` units to `general` hunters, flips them to `in_progress` with an `agent_id`, and builds each hunter prompt from nine ordered parts (role preamble, `architecture.md` verbatim, assigned unit ids and block map, the selected attack-class blocks "copied verbatim", exclusions with reasons, hunting method, candidate gate, prior-confirmed exclusions, scratch paths and result contract). Hunters "return exactly one JSON object, with no surrounding prose". After each wave a fresh `research` coverage critic reads the ledger and source and returns `missing_units`, `reassign_ids`, `resolved_prior_leads`, `stop`. In `standard`/`deep` a second, distinct "final-clean critic" must also return no work before coverage is called complete.

**Phase 3 — candidate validation** (`VALIDATION-AND-REPORTING.md`): every unique candidate goes to "a fresh `general` verifier that did not hunt it". Prompt opens: "You did not write this candidate. Try to refute it from repository source and bounded local evidence." Returns `{"decision": "confirmed|needs_validation|rejected", "record": {...}}`.

**Phase 4 — structured output:** the parent writes `findings.json` sorted by fingerprint and runs `node <skill-dir>/validate-findings.cjs` and `node <skill-dir>/validate-coverage-ledger.cjs`. "Validator success proves format and ledger consistency only."

**Phase 5 — record verification:** one more fresh `research` verifier per final `confirmed` and `needs_validation` record, returning `verified` or `replace`. A material replacement (stronger verdict, changed root cause, trace, observed result, impact or severity) is not applied until yet another fresh verifier agrees.

**Phase 6 — reports:** `REPORT.md`, `FINDINGS-DETAIL.md`, `NEEDS-VALIDATION.md` are derived from the final records and ledger. "The prose files never change a verdict, severity, blocker, or demonstrated impact."

**Terminal states** (`SKILL.md`): "Do not end the run before one of exactly two terminal states: (a) all Phase 6 artifacts are written and both validators pass, or (b) `run_status: "incomplete"` is recorded with its exact reason and the gap is disclosed in the report."

## 3. Mechanisms

Evidence note that applies to all items: the repository contains no eval set, benchmark, results table, or postmortem. The only outcome statements are (a) README: "In our test runs, a single run found roughly half of the vulnerabilities that repeated runs found in total" (no numbers, targets or method given) and (b) the body of commit `158eb44`: "Validated end to end with a live budget-limited audit run against an internal repository: both validators passed and the run reported honest partial coverage" (one run, not reproducible). Where an item says "no evidence found" it means nothing beyond these two statements.

1. **Guidance-by-default mode gate.** Loading the skill does not start the six-phase run or create files; ambiguous requests get one clarifying question. Lives in `SKILL.md` "Operating modes" (added in the last commit, `c1c8a8c`). Solves: a skill auto-triggering an expensive multi-agent run and writing files on a casual security question. Evidence: no evidence found; the fact it was added three months after launch suggests the problem was observed.

2. **Coverage ledger as the coverage claim.** `coverage-ledger.json` is a JSON array of units (surface x boundary x subsystem x attack class, optional lifecycle). "The ledger is the coverage claim. An architecture summary, agent count, or generic 'auth reviewed' sentence is not coverage evidence." Lives in `RECONNAISSANCE.md` "Deterministic coverage ledger". Solves: unfalsifiable "we reviewed auth" statements and silently skipped areas. Evidence: no evidence found beyond the commit note above.

3. **Canonical, collision-checked unit ids.** `coverage_id` is built from source-derived `canonical_refs`, each percent-encoded (RFC 3986 unreserved set) and joined with `::`; no wave, agent, verdict, severity or line number may appear. The validator recomputes the id (`canonicalCoverageId`) and rejects mismatches, duplicates, unsorted order, and one semantic tuple under two ids. Lives in `RECONNAISSANCE.md` and `validate-coverage-ledger.cjs` (`encodeCanonicalRef`, `validateDocument`). Solves: ids that drift between runs, so prior coverage cannot be matched. Evidence: unit tests ("derives collision-free canonical IDs from exact UTF-8 references", "rejects aliases for one semantic tuple"); no field evidence.

4. **Per-state field invariants (state machine).** A fixed table says which fields each status (`planned`, `in_progress`, `blocked`, `covered`, `candidate`, `not_applicable`, `out_of_scope`, `deferred`) may or must carry; e.g. `covered` needs an owner plus non-empty `reviewed_paths` and `local_checks` and no fingerprints; `deferred` needs a reason and no evidence. Lives in `RECONNAISSANCE.md` (table) and `validate-coverage-ledger.cjs` (`validateStateInvariants`). Solves: units closed without evidence, or partial evidence hidden in a "deferred" unit. Evidence: test "enforces state evidence"; no field evidence.

5. **Check ownership.** Every check carries its own `agent_id` and `reviewed_paths`; unit-level `reviewed_paths` must equal the union; a `source` check must have `artifact: null`; a `local` check must point under `agents/<check.agent_id>/artifacts/`. Lives in `validate-coverage-ledger.cjs` (`validateChecks`, `validateReviewedPathOwnership`, `isOwnedArtifactPath`). Solves: one agent claiming another agent's evidence. Evidence: tests; note the artifact check is a string-prefix check only (see section 4).

6. **Append-only attempts archive with fresh owner.** When a critic reopens a unit, the old terminal state is appended to `attempts` with a `reassignment_reason`; the new attempt gets a higher `wave`, a different `agent_id`, and empty live evidence; archived artifacts cannot be reused. Lives in `RECONNAISSANCE.md` and `validate-coverage-ledger.cjs` (`validateAttempts`). Solves: re-review overwriting provenance, or the same agent re-reviewing itself. Evidence: tests ("rejects reassignment owner reuse and evidence mixing"); no field evidence.

7. **Verbatim prompt assembly from named blocks.** Hunter prompts must contain the selected attack-class blocks "copied verbatim ... Do not send block or companion names alone", plus an explicit list of excluded blocks with reasons; the block map is stored per ledger unit so it is "machine-checkable". Lives in `HUNTING.md` "Required hunter prompt"; block sources are `ATTACK-CLASSES.md` and ten companion files that share one section layout (`When to use this file`, `Core discipline`, class sections, `Universal moves`, `Validation rules`). Solves: sub-agents that never see the checklist the parent thinks it sent; companions selected by keyword rather than by boundary ("Do not select a companion file merely because the language or dependency name appears"). Evidence: no evidence found. The validator checks only that a block is not both selected and excluded; it does not check that the referenced block exists in the file.

8. **Candidate gate.** Seven rules included in every hunter prompt: complete repository-relative trace, bounded local observed result for a proposed `confirmed`, no strengthening ("Do not strengthen a crash into code execution"), `needs_validation` when a fact is not observable, missing best practice is not a finding, stable fingerprint, "Return an empty candidate array when nothing survives these gates." Lives in `HUNTING.md` "Core validation rules". Solves: checklist deviations and speculative findings. Evidence: no evidence found.

9. **Structured-only results; malformed output is discarded, not repaired.** Hunters, critics and verifiers return exactly one JSON object. "Discard a malformed or prose-wrapped verifier result without repairing it; re-run that candidate with a fresh verifier". A failed or malformed hunter result "leaves that unit `planned` for reassignment". Lives in `HUNTING.md` and `VALIDATION-AND-REPORTING.md`. Solves: the parent rewriting a sub-agent's conclusion (which would break independence) and prose that cannot be deduplicated. Evidence: no evidence found.

10. **Coverage-critic loop with a two-critic stop rule.** After each wave a fresh critic "proposes coverage, not findings". In `standard`/`deep`, coverage is complete only when the post-wave critic and a separately reserved final-clean critic both return no accepted work. "Never use a silent wave or agent cap as evidence of complete coverage." Lives in `HUNTING.md` "Coverage-critic waves". Solves: the planner's own blind spots in the initial ledger; stopping because agents ran out. Evidence: no evidence found.

11. **Fresh adversarial verifier per candidate (Phase 3).** Verifier did not hunt the candidate, is told to refute it, must "re-read every cited current source location", and "must not receive another verifier's conclusion". Its input is limited to the candidate, linked checks, needed architecture facts, relevant validation blocks, and the schema. Lives in `VALIDATION-AND-REPORTING.md`. Solves: self-confirmation of findings by the agent that produced them. Evidence: no evidence found (README states the principle: "The agent that checks a finding is never the agent that found it").

12. **Second fresh verification of final records (Phase 5), including `needs_validation`.** "Do not verify only `confirmed` records. A misleading `needs_validation` handoff wastes owner time and can preserve a false premise." Material replacements need a third independent agent; if none is available the record is removed and the run is marked incomplete. Lives in `VALIDATION-AND-REPORTING.md` Phase 5. Solves: errors introduced when the parent merges verifier corrections into the final record; a verifier silently upgrading a verdict. Evidence: no evidence found.

13. **Three-verdict schema with mutually exclusive fields.** `report-schema.json` is a top-level array whose items are `oneOf` three branches, each `additionalProperties: false`: `confirmed` (requires `root_cause`, `intended_behavior`, `trace`, `evidence`, `conditions`, `execution`, `remediation`, `severity`, `confidence`), `needs_validation` (requires `claimed_root_cause`, `blockers`, `validation_plan`; no severity), `rejected` (requires `claimed_root_cause`, `reason`). `validate-findings.cjs` adds semantic checks: sorted and unique fingerprints, positive line numbers, safe repository-relative paths, trace must run `entrypoint` → `propagation`* → `sink`, forbidden fields per verdict. Solves: "probably vulnerable" findings carrying a severity; prose and data disagreeing. Evidence: 34 tests in `validate-findings.test.cjs`; not run here.

14. **Severity capped at demonstrated impact, in code.** Error text: "severity.overall_severity: cannot exceed demonstrated impact". `SKILL.md` adds calibration anchors per level and the rule "If you cannot state the concrete damage, the severity is lower than it feels." Lives in `validate-findings.cjs` (`collectFindingSemanticErrors`, `SEVERITY_RANK`) and `SKILL.md` "Separate priority from certainty". Solves: severity inflation. Evidence: test "rejects severity above demonstrated impact"; the impact score itself is model-assigned, so the cap only enforces internal consistency.

15. **Rejected records retained as memory.** `rejected` records stay in `findings.json` "so future runs do not repeat the unsupported claim without changed evidence"; a prior rejection "suppresses only that exact claim, not review of the coverage unit". Lives in `VALIDATION-AND-REPORTING.md` Phase 4 and `RECONNAISSANCE.md` "Prior-run input". Solves: re-litigating the same false positive each run. Evidence: no evidence found.

16. **Prior-run carry rules.** Runs are additive. A prior `confirmed` is carried only if its source is unchanged, and still goes through current verification; changed source creates a revalidation unit; prior `needs_validation`, `deferred`, `blocked`, `out_of_scope` "never suppress a current unit"; a prior `quick` or scoped ledger contributes "never an implied 'rest is fine.'" Tracked per unit in `prior_status` (11 allowed values). Lives in `SKILL.md` "Coverage and prior runs" and `RECONNAISSANCE.md`. Solves: stale findings re-reported, and stale "covered" marks hiding changed code. Evidence: the README's "roughly half" statement is the stated motivation; no data.

17. **Hunter exclusion list limited to fingerprint, title, root cause.** Carried confirmed findings are given to hunters only as exclusions; anti-pattern 8: "using them as exemplars that anchor the hunt". Lives in `HUNTING.md` prompt part 8 and `SKILL.md` "Anti-patterns". Solves: hunters rediscovering known issues, or anchoring on them. Evidence: no evidence found.

18. **Stable source-derived fingerprint.** Same fingerprint for the same root cause in every state; pattern `^[A-Za-z0-9][A-Za-z0-9._:/@+-]*$`; must not include line, wave, agent, severity or verdict. Used to deduplicate candidates, link ledger units to records, and match across runs. Lives in `HUNTING.md` gate rule 6, `report-schema.json`. Solves: duplicate findings and broken cross-run matching. Evidence: no evidence found; how the fingerprint is derived is left to the model (see section 4).

19. **Run profiles.** `quick` (one hunter wave, one critic, one verifier per candidate, critic discoveries recorded as `deferred`), `standard`, `deep` (per-subsystem and lifecycle units, critics to a clean pass, second pass on previously covered units). "Profiles change breadth and redundancy, never the evidence bar." Scoped runs record everything else as `out_of_scope` — "never as `covered`". Lives in `SKILL.md` "Run profiles and scope". Solves: cost control without lowering the confirmation bar; partial runs presenting as complete. Evidence: no evidence found.

20. **Agent-invocation budget with reserves.** Budget is a maximum count of agent invocations. Before any agent launches the parent reserves four reconnaissance calls, the required critics and at least one verifier; verifier reserve "about 1 or 2 agents per expected candidate; when in doubt reserve 30% of the balance". If reserves do not fit, no hunters launch and units become `deferred` with reason `budget_cannot_reserve_critics_and_validation`. Lives in `SKILL.md` "Cost budget", `HUNTING.md`. Solves: spending everything on hunting and having nothing left to verify. Evidence: the single internal run in the `158eb44` commit note.

21. **Explicit incomplete-run state with named reasons.** `run_status: "incomplete"` plus `incomplete_reason` (`budget_cannot_fund_reconnaissance_and_reserves`, `critic_budget_exhausted`, `validation_budget_exhausted`). An unvalidated candidate "does not enter `findings.json` under any verdict" and the report's first section must list affected fingerprints. Lives in `SKILL.md`, `VALIDATION-AND-REPORTING.md`. Solves: a truncated run reporting as a clean one; unverified candidates being relabelled `needs_validation`. Evidence: same single commit note ("the run reported honest partial coverage").

22. **Deterministic hunter priority order.** Rank: lowest-trust entry surfaces first, then most valuable protected resources, then prior-run gaps and changed source, then historically productive classes; "Ties break lexicographically by `coverage_id` so runs stay deterministic." Lives in `HUNTING.md`. Solves: arbitrary coverage when the budget cannot reach everything. Evidence: no evidence found.

23. **Single-writer rule for shared files.** "The parent creates and is the only writer of shared run files" (seven named files). Each sub-agent gets `<output-dir>/agents/<agent-id>/scratch/` and a parent-owned `artifacts/`. Agent ids must match `^[a-z0-9][a-z0-9_-]{0,63}$` and not be a Windows device name. Lives in `SKILL.md` "Write isolation"; id rule also in the ledger validator (`isSafeAgentId`). Solves: concurrent agents corrupting shared state; case-fold directory collisions. Evidence: no evidence found. Enforcement is by prompt unless the host restricts sub-agent writes.

24. **Sandbox precondition for running target code.** Target builds, tests and fixtures run "only inside an OS-enforced sandbox" with four controls: no external network, empty allowlisted environment, read-only target and toolchain with scratch-only writes, low CPU/memory/process/file/disk/time limits. "If every control cannot be enforced, do not execute target code: report the missing sandbox capability as a needs-validation blocker". Also "Do not install dependencies or let builds fetch them." Recon agent 1d is asked whether the platform can enforce these. Lives in `SKILL.md` "Universal execution safety", repeated in hunter and verifier prompts. Solves: a hostile or simply side-effectful repository executing on the auditor's host with credentials. Evidence: no evidence found. The skill ships no sandbox; it only describes the requirement.

25. **Artifact promotion procedure.** An 11-step procedure for copying evidence out of scratch: retained directory descriptors, no-follow walks, `fstat` regular-file and link-count-one checks, size limits before and during read, exclusive destination creation, "Never recursively copy or glob scratch". The same fenced block is embedded in `SKILL.md`, `HUNTING.md` and `VALIDATION-AND-REPORTING.md`, labelled "Reference only for you: the parent performs these steps". Solves: symlink, hard-link and race attacks from target-controlled output into the retained evidence directory. Evidence: no evidence found. No implementation is shipped (see section 4).

26. **No-live-probing boundary.** "Do not probe deployed endpoints, external services, shared infrastructure, production identities, other users' data, or live control planes." Deployment facts not in the repository must become `needs_validation` with "the exact missing fact and a safe owner-observed or local plan"; reports contain "no live-probe instructions". Lives in `SKILL.md`, every sub-agent prompt, Phase 6. Solves: an audit agent attacking production; guessing at proxy or cloud configuration. Evidence: no evidence found.

27. **Stop at the minimum effect.** Local checks "Stop at a wrong return value, unauthorized dummy record, sanitizer finding, policy difference, or other minimum effect" and must not "produce persistence, post-fault, or concealment material". Lives in `SKILL.md` "Use bounded local evidence", `HUNTING.md`. Solves: the audit producing a working exploit chain. Evidence: no evidence found.

28. **Environment-capture rule for reproduction records.** Record "only the allowlisted environment variable names plus safe non-secret values ... Launch from an empty environment rather than trying to redact one after execution." Lives in `SKILL.md`. Solves: host secrets leaking into retained evidence. Evidence: no evidence found.

29. **Hardened validators.** Both validators open the input with `O_NOFOLLOW | O_NONBLOCK`, `fstat` for a regular file, enforce a 5 MiB limit before and during read, require valid UTF-8, bound nesting depth (64), counts, and error output (100 messages), and escape control and format characters in diagnostics (`safeQuote`, `escapeUnsafeDiagnosticCharacters`). The ledger validator does a streaming text preflight before `JSON.parse`. They refuse to run where the OS flags are missing ("OS no-follow and nonblocking input protection is unavailable"). Lives in `validate-findings.cjs`, `validate-coverage-ledger.cjs`. Solves: the validator being attacked by a model- or target-influenced JSON file (resource exhaustion, terminal-control injection into the parent's context). Evidence: 31 + 34 tests (`node:test`), including FIFO, symlink, constrained-heap and control-character cases; not run here; no CI in the repo runs them.

30. **Report derived from records, written last.** Phase 6 starts "Only after Phase 5 passes for every record retained in `findings.json`"; anti-pattern 10: "Writing the report before independent verification or letting prose and JSON disagree." Reports must state partial coverage plainly and "A clean run may have zero confirmed records. State that result ... without inventing LOW findings." Lives in `VALIDATION-AND-REPORTING.md` Phase 6. Solves: narrative reports that overstate or pad. Evidence: no evidence found; nothing mechanically checks the prose against the JSON.

31. **Attack-class prompt library, including "Wildcard" and "Obvious things" hunters.** Seven ordinary classes plus a category-free hunter ("Read code that looks boring or disconnected from security") and a literal checklist hunter ("This agent does not need to be creative. It needs to be thorough and literal") which must still "verify the full code path ... A flag is not a finding". Ten domain companions. Lives in `ATTACK-CLASSES.md` and the companion files. Solves: gaps between named categories; basics nobody checks. Evidence: no evidence found.

32. **Domain rule for LLM targets.** "Prompt injection alone is not a finding. Require a code-level boundary failure"; "A guardrail prompt is not a security boundary. Count only deterministic checks, resource-scoped authorization, isolation, binding, and constrained credentials." Lives in `AI-AND-LLM.md` "Core discipline". Solves: low-value "the model can be prompt-injected" findings. Evidence: no evidence found.

33. **Comparable-software baseline for calibration.** Recon agent 1a names a comparable product if source-grounded; it is used "to calibrate effort and severity, never to dismiss a demonstrated finding". Lives in `RECONNAISSANCE.md` "Architecture summary". Solves: severity judged without reference to accepted practice. Evidence: no evidence found.

34. **Anti-pattern list.** Ten named failure modes at the end of `SKILL.md` (checklist deviations as vulnerabilities, defense-in-depth advice as findings, guessed deployment behavior, self-impact as cross-boundary, severity on `needs_validation`, and so on). Solves: recurring low-quality audit output. Evidence: no evidence found.

## 4. Known weaknesses, open issues, criticisms

Observed from the source (issue tracker content is Unverified — not reachable):

- **Almost everything is prompt-enforced.** The validators check the two JSON files only. Agent freshness, verifier independence, "parent is the only writer", verbatim prompt assembly, budget accounting, and the sandbox are instructions the parent model may or may not follow. Nothing records which agent actually produced what; `agent_id` values are strings the parent writes.
- **The validators do not cross-check each other.** Each takes one file path. Nothing verifies that every `result_fingerprints` entry in the ledger has a record in `findings.json`, or the reverse, or that `run-metadata.json` agrees with either.
- **Artifact existence is not checked.** `isOwnedArtifactPath` is a string-prefix test (`agents/<agent-id>/artifacts/`); a ledger can cite a local-check artifact that does not exist and still pass.
- **Truth is not checked.** The doc says so itself: "Validator success proves format and ledger consistency only." A fabricated `file`/`line` trace with valid shape passes; only the later model verifiers stand between that and the report.
- **No sandbox and no promotion code are shipped.** The 11-step promotion procedure needs descriptor-relative no-follow syscalls that a coding agent with a shell cannot perform as written. In most hosts the honest outcome is "do not execute", so findings needing a local observed result would stay `needs_validation`. A less careful agent may run target code anyway and call it sandboxed.
- **Fingerprint derivation is unspecified.** Only the character pattern and "source-derived, no line/wave/agent" are given. Cross-run deduplication and rejected-claim suppression depend on different agents in different runs producing the same string for the same root cause.
- **Ledger seeding is model judgment.** "Every material combination" is decided by the parent. The ledger makes gaps visible only for surfaces someone listed; the critics are the only check on surfaces never listed.
- **Cost.** Minimum for `standard` is 4 recon + hunters + 2 critics + up to 2 verifiers per candidate, with repeated waves. The README says one run finds "roughly half" of what repeated runs find, so the stated expectation is several runs per target. No token or dollar figures are given.
- **Prompt size.** Every hunter prompt carries `architecture.md`, verbatim class blocks, the hunting method, the gate, the promotion block and two schema branches. The promotion block is told to hunters as "Reference only for you" — pure context cost.
- **Triplicated text.** The promotion block must stay "byte-identical" across three files; nothing in the repo checks that. One test ("keeps shared helpers aligned with the coverage-ledger validator") exists because the two validators duplicate helper code.
- **Validators are unusable on Windows.** They throw when `O_NOFOLLOW`/`O_NONBLOCK` are unavailable ("Node exposes no race-safe fallback on these platforms, so reject all inputs"). On native Windows the Phase 4 gate cannot pass, so a compliant run cannot reach the "complete" terminal state there. (Inferred from the code; not executed.)
- **No measured results.** No benchmark, no false-positive rate, no comparison against a baseline audit prompt, no example run output in the repo.
- **Maintenance signals.** One maintainer; no tags, releases or changelog; no CI to run the 65 tests; one very large rework commit (`158eb44`, +4,792/−701 across 21 files) that changed the findings contract with no version marker; last commit 2026-09-14; most external PRs appear unmerged (inference from pull refs).
- **Verbosity risk.** `SKILL.md` alone is about 22 KB of dense rules with many cross-references; adherence by weaker models to rules such as the budget reserve arithmetic is untested in the repo.

## 5. Anything that looks unsafe

- **Hidden instructions:** none found. All 22 files scanned for Unicode format/control/private-use characters and HTML comments: zero hits in the Markdown, schema and validators. The only unusual characters are in `validate-findings.test.cjs`, where they are deliberate test inputs for the control-character rejection tests.
- **Install scripts:** none. No `package.json`, no lifecycle scripts, no shell scripts, no hooks, no settings or permission files, no MCP configuration. Install is `npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit` — that runs the third-party `skills` CLI (skills.sh), which was not reviewed here. With no tags, the install tracks `main` and cannot be pinned to a release, only to a commit.
- **Validator code:** imports only `fs`, `path`, `util` (`node:` built-ins). No network, no `child_process`, no `eval`, no environment reads, no writes. Reads the one input path, and `validate-findings.cjs` also reads `report-schema.json` beside itself. The test files use `child_process.spawnSync` to run the validator with the current Node binary and write fixtures to an OS temp directory; they are not part of the audit workflow.
- **External URLs in the docs:** `skills.sh`, the repo's own URL, and the Cloudflare blog post. None is something the agent is told to fetch.
- **Permissions the workflow asks for:** broad read of the target repository; write to `~/security-audit-skill/<repo-name>/run-<N>` in the user's home by default; spawning many sub-agents; running `node` on the two validators. Running target code is conditional on a sandbox the skill does not provide — this is the main practical risk: on a host without a real sandbox, safety depends on the model declining to execute.
